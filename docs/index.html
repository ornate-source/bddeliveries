One way to send a parcel,three couriers to carry it.

BDDeliveries is a small Node.js library that talks to Pathao, Steadfast and Paperfly using the exact same instructions. Learn it once, and switching or adding a courier becomes a one-word change.

Get started One shop or a marketplace?
0 couriers Node 18+ Zero dependencies TypeScript included 0 tests

Never done this before? Start here.

Skip ahead if you already integrate courier APIs for a living.

The travel-adapter analogy. Every country has a different wall socket. Rather than buying a new charger for each one, you carry a single universal adapter.

Couriers are the sockets. Each one speaks its own language, wants its own passwords, names the same field three different ways, and answers in its own shape. BDDeliveries is the adapter that lets your code plug into any of them the same way.

Some words you'll see everywhere

Word What it actually means
Courier / gateway A company that carries your parcel — Pathao, Steadfast, Paperfly. In code you always pass one as gateway: 'pathao'.
Order / consignment One parcel going to one customer. You create it; the courier picks it up.
Invoice Your own reference for the order — an order number from your shop. You choose it. Keep it unique.
Tracking ID The courier's reference, handed back after the order is created. Use it to ask "where is my parcel?"
COD Cash on Delivery — the rider collects money at the door and the courier pays you later. codAmount is how much to collect.
Credentials The username, password or API keys the courier gave you when you signed up as a merchant. Secret. Never put them in front-end code.
Sandbox A fake version of the courier's system for testing, where no real parcel moves. Only Pathao has one.

This library runs on your server, never in a browser. Your courier credentials would be visible to anyone who opened DevTools. Call it from your backend — Express, Fastify, a Next.js route handler, a cron job.

Everything is three actions

That's the whole library. Every courier, the same three functions.

createOrder()

Book a parcel for pickup. You get back a tracking ID.

trackOrder()

Ask where the parcel is right now.

cancelOrder()

Call off a booking — where the courier actually supports it.

Only the gateway value changes between couriers. The rest of your code stays identical:

await createOrder({ gateway: 'pathao',    /* …same fields… */ });
await createOrder({ gateway: 'steadfast', /* …same fields… */ });
await createOrder({ gateway: 'paperfly',  /* …same fields… */ });

Your first order, end to end

Three steps from an empty file to a booked parcel.

  1. Put your credentials in a .env file

    Never commit this file. Your courier gave you these when you signed up as a merchant.

    PATHAO_CLIENT_ID=your-client-id
PATHAO_CLIENT_SECRET=your-client-secret
PATHAO_USERNAME=you@shop.com
PATHAO_PASSWORD=your-password
PATHAO_STORE_ID=123456

  2. Tell the library about them, once, at startup

    import { configure } from 'bddeliveries';

configure({
  pathao: {
    clientId:     process.env.PATHAO_CLIENT_ID,
    clientSecret: process.env.PATHAO_CLIENT_SECRET,
    username:     process.env.PATHAO_USERNAME,
    password:     process.env.PATHAO_PASSWORD,
    storeId:      process.env.PATHAO_STORE_ID,
  },
});

  3. Book the parcel

    import { createOrder } from 'bddeliveries';

const order = await createOrder({
  gateway: 'pathao',
  invoice: 'INV-1001',                 // your own order number
  recipientName: 'John Doe',
  recipientPhone: '01711111111',
  recipientAddress: 'House 12, Road 5, Dhanmondi, Dhaka',
  codAmount: 1500,                     // taka to collect at the door
});

console.log(order.trackingId);         // save this in your database
console.log(order.status);             // "pending"

Store order.trackingId against your order row. It is the only way to ask the courier about this parcel later. If you lose it, you are down to phoning support.

Which one are you?

This one decision changes how you set up credentials. Get it right now and nothing later will surprise you.

Most people

A single shop

You run one business. There is one Pathao account, one Steadfast account. Every parcel ships under your own merchant account.

→ Use configure(). Set it once when your server boots and forget about it.

Platforms & SaaS

A marketplace

You host many sellers. Each seller has their own Pathao account, and parcels must ship under their account, not yours.

→ Use DeliveryClient. One client per seller, each with its own credentials.

Marketplaces: do not use configure(). It stores credentials in one shared place for the whole process. If two sellers' requests overlap, the second configure() overwrites the first — and a parcel can be booked under the wrong seller's account. DeliveryClient exists precisely to prevent this.

Setup: a single shop

Call configure() once, then call the three actions from anywhere. 

// setup.js — imported once when your server starts
import { configure } from 'bddeliveries';

configure({
  pathao: {
    clientId:     process.env.PATHAO_CLIENT_ID,
    clientSecret: process.env.PATHAO_CLIENT_SECRET,
    username:     process.env.PATHAO_USERNAME,
    password:     process.env.PATHAO_PASSWORD,
    storeId:      process.env.PATHAO_STORE_ID,
  },
  steadfast: {
    apiKey:    process.env.STEADFAST_API_KEY,
    secretKey: process.env.STEADFAST_SECRET_KEY,
  },
});
// routes/checkout.js — anywhere else in your app
import { createOrder } from 'bddeliveries';

const order = await createOrder({
  gateway: 'steadfast',
  invoice: 'INV-1002',
  recipientName: 'Ayesha Rahman',
  recipientPhone: '01811111111',
  recipientAddress: 'Flat 4B, House 9, Banani, Dhaka',
  codAmount: 2300,
});

Shortcut: if your environment variables use the standard names (see Env variables), you can skip configure() entirely — the library reads them automatically.

Setup: a marketplace

One DeliveryClient per seller. Their credentials never touch anyone else's.

import { DeliveryClient } from 'bddeliveries';

// Build a client from whatever you have stored for this seller
function clientFor(seller) {
  return new DeliveryClient({
    pathao: {
      clientId:     seller.pathaoClientId,
      clientSecret: seller.pathaoClientSecret,
      username:     seller.pathaoUsername,
      password:     seller.pathaoPassword,
      storeId:      seller.pathaoStoreId,
    },
  });
}

// Two sellers, two clients, zero chance of crossing wires
const order = await clientFor(seller).createOrder({
  gateway: 'pathao',
  invoice: `INV-${orderId}`,
  recipientName: buyer.name,
  recipientPhone: buyer.phone,
  recipientAddress: buyer.address,
  codAmount: total,
});

A DeliveryClient exposes the same three actions as the global functions, plus callGateway(). It also caches courier login tokens per seller, so sellers never share a session.

Where do seller credentials live? In your database, encrypted at rest. Build the client on demand for each request — creating one is cheap.

How credentials are found

Three places are checked, in this order. The first one that has a value wins.

1

Passed into the call Marketplace

createOrder({ gateway: 'pathao', clientId: '…' }) — beats everything below.

2

Set with configure() Single shop

Your app-wide defaults, set once at startup.

3

Environment variables Fallback

Read automatically from process.env. Handy for local development.

Only real credentials are picked up from a call. Order fields like recipientName are kept well away from the credential object, so a customer named "password" can never overwrite your login. Missing credentials throw MISSING_CREDENTIALS and name exactly which keys are absent.

The parcel journey

What actually happens between a customer clicking "Order" and a parcel arriving at their door.

Customer
Places an order

On your website

Your server
createOrder()

Gets a tracking ID back

Courier
Picks it up

A rider collects from you

Courier
In transit

Through sorting hubs

Customer
Delivered

Pays COD at the door

Your code is only involved in step 2. After that you poll trackOrder() — on a schedule, or when a customer asks — to follow steps 3 to 5.

There are no webhooks. None of these three couriers reliably calls your server when a parcel moves. You have to ask. A cron job that tracks all open orders every 15–30 minutes is the normal pattern — don't poll every order every minute, you will get rate-limited.

The three couriers

What each one needs from you, and what it can actually do.

Pathao

Nationwide coverage and the most complete API of the three. Needs a store ID because one merchant account can have several pickup locations.

clientId · clientSecret · username · password storeId required Has a sandbox Create Track No cancel

Steadfast

Simple key-based login and by far the richest set of extras — account balance, bulk orders, return requests, payment history.

apiKey · secretKey 8 extra operations No sandbox Create Track No cancel

Paperfly

Username/password login plus a separate merchant key. Tracks by your invoice number rather than a courier-issued ID.

username · password · paperflyKey No sandbox Create Track Cancel unverified

Create an order

The same five fields work everywhere. Each courier then adds a few of its own. 

const order = await createOrder({
  gateway: 'pathao',
  invoice: 'INV-1001',
  recipientName: 'John Doe',
  recipientPhone: '01711111111',
  recipientAddress: 'House 12, Road 5, Dhanmondi, Dhaka',  // 10 chars minimum
  codAmount: 1500,

  // Pathao-specific
  storeId: 123456,        // or PATHAO_STORE_ID / configure()
  itemWeight: 1.5,        // kg, between 0.5 and 10
  itemQuantity: 2,
  cityId: 1,              // optional: Pathao's own area codes
  zoneId: 52,
});

order.trackingId;   // Pathao consignment id, e.g. "DA290124ABCDE"
order.status;       // "pending"
const order = await createOrder({
  gateway: 'steadfast',
  invoice: 'INV-1002',
  recipientName: 'Ayesha Rahman',
  recipientPhone: '01811111111',
  recipientAddress: 'Flat 4B, House 9, Banani, Dhaka',
  codAmount: 2300,

  // Steadfast-specific
  alternativePhone: '01911111111',
  note: 'Call before delivery',
});

order.trackingId;    // consignment id, e.g. "987654"
order.trackingCode;  // also returned, e.g. "TRK-987654"
const order = await createOrder({
  gateway: 'paperfly',
  invoice: 'INV-1003',
  recipientName: 'Karim Uddin',
  recipientPhone: '01611111111',
  recipientAddress: 'Road 3, Uttara Sector 7, Dhaka',
  codAmount: 900,

  // Paperfly-specific
  storeName: 'Main Warehouse',
  maxWeight: 1,
});

order.trackingId;              // your own invoice — "INV-1003"
order.providerTrackingNumber;  // Paperfly's number, if returned

Phone numbers are cleaned up for you. +8801711111111, 8801711111111, 017 1111 1111 and 017-1111-1111 all become 01711111111 before being sent. Anything that isn't a real Bangladeshi mobile number is rejected before the request leaves.

Track an order

Ask the courier where the parcel is. Same call for every courier.

const result = await trackOrder({
  gateway: 'pathao',
  trackingId: 'DA290124ABCDE',     // the id you saved at creation
});

result.status;          // "in_transit"  — always one of the canonical values
result.providerStatus;  // "In_Transit"  — Pathao's own wording, untouched
result.raw;             // the courier's full response, if you need it

Steadfast and Paperfly can look an order up by your own invoice number — useful if you never stored the courier's ID.

// Steadfast: by invoice, or by tracking code
await trackOrder({ gateway: 'steadfast', invoice: 'INV-1002' });
await trackOrder({ gateway: 'steadfast', trackingCode: 'TRK-987654' });

// Paperfly always tracks by your invoice
await trackOrder({ gateway: 'paperfly', trackingId: 'INV-1003' });

Because there are no webhooks, this is how most apps keep order status up to date.

import { trackOrder, STATUS } from 'bddeliveries';

const DONE = [STATUS.DELIVERED, STATUS.RETURNED, STATUS.CANCELLED];

// Run every 15–30 minutes
for (const order of await db.findOpenOrders()) {
  try {
    const { status, providerStatus } = await trackOrder({
      gateway: order.gateway,
      trackingId: order.trackingId,
    });

    await db.updateOrder(order.id, { status, providerStatus });
    if (DONE.includes(status)) await db.closeOrder(order.id);
  } catch (error) {
    // One bad order must not stop the whole batch
    console.error(order.id, error.code, error.message);
  }
}

Statuses

Every courier invents its own words for the same few things. We translate them into one list.

pending picked_up in_transit delivered partial_delivered returned cancelled on_hold failed unknown

Write your switch against status and it will keep working when you add a courier. Need the courier's exact wording — for a support screen, say? It is always there as providerStatus.

Courier says You get as status
Pathao Pickup_Requested pending
Pathao At_the_Sorting_HUB in_transit
Steadfast partial_delivered partial_delivered
Steadfast hold on_hold
Paperfly inTransit: true in_transit
Anything we don't recognise unknown

Why unknown instead of passing the raw word through? Because a surprise value silently falling into your else branch is how parcels get marked delivered when they weren't. unknown is honest, and providerStatus still tells you exactly what the courier said.

Cancel an order

Read this before you build a "Cancel" button.

Pathao and Steadfast cannot cancel through their APIs. Calling cancelOrder() on either one throws NOT_SUPPORTED. That is deliberate.

An earlier version of this library returned { status: 'cancelled' } for Steadfast without contacting the courier at all. Shops marked orders cancelled in their own database while the parcel was still on a van. A loud error is far cheaper than a quiet lie.

Pathao throws NOT_SUPPORTED
Steadfast throws NOT_SUPPORTED
Paperfly implemented, unverified

So how do I actually cancel one?

  • Pathao — cancel from the Pathao Merchant Panel.
  • Steadfast — raise a return request, or use the Steadfast merchant panel.
  • Paperfly — cancelOrder() exists, but the endpoint has not been confirmed against current Paperfly documentation. Test it against your own account before relying on it.
import { callGateway } from 'bddeliveries';

// Steadfast's nearest equivalent: ask for the parcel back
await callGateway({
  gateway: 'steadfast',
  method: 'createReturnRequest',
  invoice: 'INV-1002',
  reason: 'Customer cancelled',
});

A return is not a cancellation. The parcel still travels; it just comes back to you. Don't present it to your users as a cancellation, and don't refund on the strength of the request alone.

What gets checked before anything is sent

Bad data is caught in your own process, before a courier ever sees it.

Every createOrder call is validated first. If something is missing or malformed you get a ValidationError naming the exact fields — and no network request is made, so there is no half-created order to clean up.

try {
  await createOrder({ gateway: 'pathao', recipientName: 'John Doe' });
} catch (error) {
  error.code;     // "VALIDATION_ERROR"
  error.fields;   // ["recipient_phone", "recipient_address", "merchant_order_id", "storeId"]
  error.message;  // "Missing required field(s) for pathao: …"
}

Required fields

Missing name, phone, address or invoice is caught immediately.

Real numbers

codAmount: 'abc' throws instead of quietly becoming null.

Sensible ranges

Pathao weight must be 0.5–10 kg; quantities at least 1.

Valid phone numbers

Must be a real BD mobile number once normalized.

Address length

Pathao's 10-character minimum is enforced, not faked with padding.

Safe identifiers

Invoice numbers are URL-encoded, so an odd character can't redirect the request.

Why the fuss about address length? Pathao rejects addresses under 10 characters. An earlier version padded short ones with spaces to sneak past that check — so the order was accepted and the rider got an address of blanks. We now refuse the order and tell you why.

Timeouts and safe retries

What happens when a courier's API is slow, flaky, or silent.

15-second timeout

Every request gives up rather than hanging your server forever.

Automatic retries

Reads retry twice with backoff on 5xx, 429 and network errors.

Never on createOrder

Retrying a booking would ship a second parcel. We don't.

The duplicate-parcel trap. If createOrder times out you cannot know whether the courier accepted it. Blindly calling it again is how shops end up sending the same order twice and paying twice.

The safe move: retry with the same invoice. All three couriers treat it as your unique reference, so a duplicate is rejected or merged rather than duplicated. Never generate a fresh invoice number on retry.

// Tune per gateway, or per call
configure({ pathao: { timeoutMs: 8000, retries: 3 } });

// Cancel a request from your own code (e.g. the user closed the tab)
const controller = new AbortController();
setTimeout(() => controller.abort(), 5000);

await createOrder({
  gateway: 'pathao',
  signal: controller.signal,
  /* …order fields… */
});

Pathao logins are cached for you. Pathao requires a login before every action. The token is reused until it expires, and simultaneous requests share one login instead of stampeding — so ten orders cost one login, not ten.

Testing without shipping real parcels

Read this before pointing anything at a courier for the first time.

Pathao sandbox: true works
Steadfast no sandbox — use baseUrl
Paperfly no sandbox — use baseUrl 
// Pathao has a real sandbox
configure({ pathao: { /* …credentials… */, sandbox: true } });
// or: PATHAO_SANDBOX=true

// Steadfast and Paperfly have none — sandbox:true THROWS rather than
// quietly using production. Point them at your own test server instead:
configure({ steadfast: { /* …keys… */, baseUrl: 'https://mock.internal/api/v1' } });

Why sandbox: true throws instead of being ignored. Steadfast and Paperfly publish no sandbox host. An earlier version accepted the flag and sent the request to production anyway — so a developer running "tests" was creating real parcels on a live account. Failing loudly is the only safe option.

Testing your own code

The whole library talks to the network through fetch, so you can test your integration without any courier account at all — just replace globalThis.fetch in your tests. That is exactly how this library's own 87 tests run.

Errors

Every failure is a DeliveryError with a machine-readable code. Branch on the code, never on the message text. 

import { createOrder, DeliveryError, ValidationError } from 'bddeliveries';

try {
  await createOrder({ /* … */ });
} catch (error) {
  if (error instanceof ValidationError) {
    return res.status(400).json({ fields: error.fields });   // your bug
  }
  if (error instanceof DeliveryError) {
    if (error.code === 'TIMEOUT') return retryLater();       // courier is slow
    if (error.code === 'NOT_SUPPORTED') return hideButton(); // courier can't
    console.error(error.gateway, error.code, error.statusCode);
  }
  throw error;
}
Code What went wrong What to do
VALIDATION_ERROR Your order data is missing or malformed. Nothing was sent. Fix the input. Check error.fields.
MISSING_CREDENTIALS Credentials not found in any of the three tiers. Check error.missingKeys.
MISSING_PARAM A required identifier — usually trackingId — was absent. Pass the identifier.
GATEWAY_NOT_FOUND Unknown courier name — usually a typo. See error.supportedGateways.
NOT_SUPPORTED The courier's API genuinely has no such feature. Don't offer it. Use the merchant panel.
UNSUPPORTED_OPERATION This adapter doesn't implement that method. Check getGatewayCapabilities().
NOT_FOUND The courier has no record of that order. Verify the tracking ID.
TIMEOUT The courier didn't answer in time. Retry — with the same invoice.
NETWORK_ERROR DNS, TLS or connection failure. Retry with backoff.
ABORTED You cancelled it via signal. Nothing — this is expected.
API_ERROR The courier rejected the request. Read error.message and statusCode.
INVALID_RESPONSE The courier returned something that wasn't JSON. Usually an outage or a wrong baseUrl.

Security

Short list. All of it matters.

Server only

Never import this in browser or mobile code. Credentials would be readable by anyone.

Secrets are redacted

Passwords, API keys and tokens are stripped from error payloads before they reach your logs.

Never commit .env

Once a credential is in git history, rotating it is the only fix.

Isolate tenants

Marketplaces must use DeliveryClient, not the global configure(). 

// Safe to log — secrets are already redacted
catch (error) {
  logger.error(JSON.stringify(error));
  // { name, message, gateway, code, statusCode,
  //   responseBody: { password: "[redacted]", … } }
}

Customer data is not redacted, and shouldn't be. Names, phone numbers and addresses appear in error.responseBody because you often need them to debug. Treat your logs as containing personal data and retain them accordingly.

Things only one courier can do, reached through callGateway().

steadfast getReturnRequest / getReturnRequests One return, or all of them.

Adding a courier

Four steps. You never touch config.js or index.js.

  1. Create src/gateways/mycourier.js

    One file per courier. Nothing else needs to know it exists.

  2. Export a META block

    export const META = {
  envMap: {
    apiKey: 'MYCOURIER_API_KEY',
    sandbox: 'MYCOURIER_SANDBOX',
  },
  requiredKeys: ['apiKey'],
  capabilities: ['createOrder', 'trackOrder'],
};

  3. Implement only what the courier really supports

    Use request() from src/utils.js, the validators from src/validation.js, and the canonical statuses from src/status.js.

  4. Register it in src/gateways/index.js

    One line. Adapters are loaded lazily, so an unused courier costs nothing.

The one rule. If the courier can't do something, throw NOT_SUPPORTED. Never return a success-shaped object for work that didn't happen. That single mistake — a cancelOrder that returned "cancelled" without calling anyone — is the reason this library was audited.

Common questions

The things people ask on day one.

Can I use more than one courier at the same time?

Yes — that's the point. Configure all three, then choose per order. A common pattern is picking by destination or by which courier is cheapest for that weight. Your code is identical either way; only gateway changes.

What if I only ever use one courier?

Perfectly fine. You still get validation, timeouts, retries, canonical statuses and typed errors — and if you ever add a second courier, you won't rewrite anything.

How do I know if a parcel was delivered?

Poll trackOrder() and check for status === 'delivered'. There are no webhooks from these couriers, so a scheduled job is the standard approach — see the polling example.

Why does cancelOrder throw for Pathao and Steadfast?

Because their APIs have no cancel endpoint. The alternative — returning "cancelled" without contacting anyone — is what an earlier version did, and shops ended up with cancelled orders in their database and live parcels on the road. Cancel from the merchant panel instead.

My order failed with VALIDATION_ERROR. Was anything sent?

No. Validation runs before any network call, so there is nothing to clean up. Read error.fields, fix the input, and call again.

Can I retry a failed createOrder?

Yes — but reuse the same invoice. All three couriers treat it as your unique reference, so a repeat is rejected or merged rather than creating a second parcel. Generating a new invoice number on retry is how duplicates happen.

Where do I find my Pathao storeId?

In the Pathao Merchant Panel, or by calling callGateway({ gateway: 'pathao', method: 'getStores' }). If you send a wrong one, the error message lists your real stores.

Is it safe to log the error object?

Credentials, yes — passwords, keys and tokens are redacted automatically. Customer names, phone numbers and addresses are not redacted, because you usually need them for debugging. Treat your logs as containing personal data.

Does this work with CommonJS (require)?

Not directly — the package is ESM only. In a CommonJS project use a dynamic import: const bd = await import('bddeliveries').
